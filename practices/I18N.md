# Internationalization

Authoritative for language, localization, and text direction. On this stack, bilingual parity and full
bidirectional layout are **product invariants**, not features added later.

## Default-language-first, full parity

A project declares a **default locale** and at least one other, and every user-facing string exists in
**all** of them, in parity. "Parity" is literal: a key present in one locale is present in every
locale; a screen shipped in the default language is shipped in the others simultaneously. A missing
translation is a broken build-time expectation, not a runtime fallback to the default.

*Reference implementations:* both projects are **Persian-first** with full English parity — Persian is
the default, English is a first-class equal, and neither is an afterthought.

## The typed message catalog

Every user-facing string outside product content lives once in a **typed message catalog**, keyed and
with each locale in parity ([DRY](../principles/DEVELOPMENT_PRINCIPLES.md) §1). Components read from
the catalog through the i18n service; **no inline string literals in components**. Because the catalog
is typed, a missing or misspelled key is a compile error, and a missing locale for a key is visible
rather than silently blank.

The active locale is held in the [observer store](../architecture/STATE_MANAGEMENT.md) and **persisted**
through the [storage port](../architecture/PORTS_AND_ADAPTERS.md), so a returning user keeps their
language.

## Localize domain content, not just UI chrome

The catalog covers UI strings. Product **content** (narration text, item names, advice, story fields)
is *also* localized, through a localized-text shape in the domain — not a second, ad-hoc mechanism.
The same "every locale in parity" rule applies to content fields. A single localized-text type used by
both UI and domain content is a recurring [candidate to propose upstream to the blueprint](../reuse/CROSS_PROJECT_SYNC.md).

## Bidirectional layout is mandatory

Every screen works in both **RTL and LTR**. This is not a stylesheet afterthought:

- Layout uses direction-aware constructs (logical properties, `dir`-aware flow) so mirroring is
  automatic, not hand-patched per screen.
- Both directions are **verified**, not assumed — including that horizontal layout does not overflow
  at narrow widths in either language.
- Text direction follows the content's locale, and mixed-direction content (e.g. a Latin name inside
  RTL text) renders correctly.

## Acceptance

- Every key resolves in every locale; parity is checked, not eyeballed.
- Each screen is verified in every supported locale and both text directions, at a narrow mobile
  width, with no horizontal overflow. This is part of the UI
  [definition of done](../principles/WORKING_AGREEMENT.md) and of the browser
  [acceptance flow](TESTING.md).

## Rules

- Declare a default locale and full parity across all locales; a missing translation fails early.
- All UI strings live in the typed catalog; no inline literals in components.
- Localize domain content through one localized-text shape, not a parallel mechanism.
- Every screen works and is verified in RTL and LTR; persisted locale survives relaunch.
