# Working agreement

How work moves from an idea to a merge. [Development principles](DEVELOPMENT_PRINCIPLES.md) governs
_how code is designed_; this document governs _how a task is run and landed_. Both bind every change.

---

## 1. Branching and merge authority

- Start every feature, fix, refactor, docs, test, or chore task on a **dedicated branch, created
  before the first edit.** Never develop directly on `main`.
- **A task is one coherent outcome, not one message, session, or feedback round.** Clarifications,
  design iterations, review corrections, retries, and follow-up tweaks toward that outcome stay on
  its existing branch, including after a commit, until the task is merged or explicitly dropped.
  Inspect the current branch and history before creating another. A separate task, or work requested
  after the earlier task was merged, starts a new branch.
- Prefix the branch with its kind, then a concise kebab-case purpose:
  `feat/`, `fix/`, `refactor/`, `docs/`, `test/`, `chore/`.
- **Numbered phases are distinct, independently reviewable deliverables within a larger effort.**
  Each phase preserves its work in scoped commits before moving to the next. Do not create or
  increment phase branches to label feedback rounds or carry the same uncommitted work forward.
  For genuine successive phases, keep a stable purpose stem and append `-phase-N`, starting at `1`.
  Use `-phase-1` from the first branch when further phases are expected; for example,
  `fix/stability-and-correctness-phase-1`, then `fix/stability-and-correctness-phase-2`.
- **Only the repository owner authorizes a merge into `main`.** Finish the work, pass
  [pre-merge verification](#pre-merge-verification), report the result, and wait for explicit
  confirmation. Never merge, fast-forward, rebase onto, or force-push `main` on your own initiative.
- **One branch is one coherent task.** An unrelated finding becomes its own branch, not a passenger.
- **Splitting a request across branches does not split the responsibility for finishing it.** When a
  request needs several branches, name them and their merge order in the first report, then carry the
  whole set to completion: after each confirmed merge, rebase the next branch on the updated `main`,
  complete its pre-merge verification, and present it for review unprompted. The request stays open
  until every branch is merged or explicitly dropped.

Enforce this rule in depth wherever the current environment exposes reliable controls: direct-editor
hooks, classified shell-command hooks, versioned commit hooks, and remote branch protection. Record
any mutation path the environment cannot intercept; no single local guard covers every client or
intentional bypass. Treat enforcement as a backstop, not a reminder. See
[AI agent workflow](../practices/AI_AGENT_WORKFLOW.md).

### Pre-merge verification

**Execute automated test suites only at the gate before merging a task branch into `main`.** Complete
implementation and preserve its scoped commits first, then validate the final merge candidate against
the current `main`. This cadence applies to agents, local hooks, and CI: do not run tests during
ordinary edit/commit iteration, before each commit, or on every development push. It also covers
composite commands such as `check` that invoke tests.

- Run every applicable [change-specific verification gate](../practices/TESTING.md#change-specific-verification-gates)
  and record the tested branch and `main` revisions, commands, and results. Local or CI evidence for
  the same candidate and inputs satisfies the gate; do not duplicate successful runs merely to
  commit or request merge approval.
- **A failure blocks the merge.** Fix it on the task branch, commit the correction, and rerun the
  affected required gates before presenting the branch for merge. An unavailable required check
  remains pending and blocks merge readiness; it is never treated as passing.
- Changes to tested code, tests, configuration, dependencies, or the `main` base invalidate affected
  results. Revalidate the affected gates on the updated candidate before merging.
- Write and update deterministic tests alongside the behavior they cover. Deferring execution does
  not defer test coverage. Code inspection, formatting, and branch/message guards may run during
  development; they must not invoke a test suite indirectly.

## 2. Commit convention

- **Subject:** `TYPE: <imperative summary>`, where `TYPE` is uppercase. Common types: `INIT`,
  `FEAT`, `FIX`, `DOCS`, `REFACTOR`, `TEST`, `CHORE`.
  - `INIT: Implement the basic structure of the monorepo`
  - `FIX: Solve the blank-screen bug in the registration screen`
- **Body:** optional, at most one short paragraph, explaining the _why_ — never a restatement of the
  diff.
- **No tooling or agent signatures.** No co-author trailers, no "generated by" lines, no mention of
  AI or assistants anywhere in the history.

Preserve meaningful milestones as properly scoped commits on the task branch. Creating
or switching branches does not save uncommitted edits; a branch name references a commit. Refining
a homepage character and then adjusting its screen finish stays on one feature branch, with commits
preserving the useful milestones.

Git identity is per-owner and set once per machine; it is a project value, not a stack rule. Record
the actual name and email in the new project's own `CONTRIBUTING`/agreement, e.g.:

```text
Name:  <owner name>
Email: <owner email>
```

### Temporary checkpoints

Before leaving an unfinished branch for another task, inspect its status. If every uncommitted change
belongs to the current task and owner, commit them as a local temporary checkpoint. Never commit,
stash, move, or rewrite another contributor's unexplained changes merely to clean the workspace; keep
working without overlap when safe, or ask the owner how to preserve them. Do not create a linked
worktree merely to avoid a dirty workspace. Use this commit message for an owned checkpoint:

```text
TEMP: Checkpoint unfinished work to keep the workspace clean

This is an unfinished job temporarily committed to keep the Git workspace clean; delete this
checkpoint and replace it with true reviewable commits after finishing the job.
```

A `TEMP` commit is a disposable local checkpoint: never present, merge, or release it. When work
resumes, replace it with the branch's properly scoped commits before review. Use a linked worktree
only when the owner explicitly requests concurrent working trees.

## 3. Definition of done (single authoritative checklist)

This section is the one checklist for deciding whether a task is landable. Area documents own their
detailed requirements and verification methods; they link here when they mention completion rather
than restating this checklist. It applies at [pre-merge verification](#pre-merge-verification), not as
a prerequisite for intermediate commits.

- The [branch and merge-authority requirements](#1-branching-and-merge-authority) are satisfied.
- The result satisfies the [development principles](DEVELOPMENT_PRINCIPLES.md) and every applicable
  requirement in each affected authoritative area document.
- The [contract-change ordering requirement](../architecture/CONTRACTS.md#the-single-source-rule) is
  satisfied for every affected shared contract.
- The [repository-wide consistency invariant](DEVELOPMENT_PRINCIPLES.md#8-repository-wide-consistency-is-mandatory)
  passed a semantic review across every affected document.
- Every applicable [change-specific verification gate](../practices/TESTING.md#change-specific-verification-gates)
  passed; no required check was silently skipped.
- Any improvement worth proposing upstream to the blueprint is recorded in the same change. See
  [cross-project sync](../reuse/CROSS_PROJECT_SYNC.md).
- The [reporting requirements](#4-reporting-and-answering-the-owner) are satisfied.

## 4. Reporting and answering the owner

Honest reporting is part of done. State the actual result, including failures and skipped steps.
"It builds" is only true when the check actually ran and passed.

**End an answer with a `## Summary` section** whenever it carries findings, comparisons, trade-offs,
or a decision to make — including diagnostic and "which repo / what is this" questions. A single-fact
answer needs no summary.

- The summary stands alone: someone reading only it misses nothing they must act on or decide.
- Use bullets as soon as there is more than one thing to know; reserve prose for a lone point.
- Order it: the direct answer, then open decisions, then anything deliberately left undone.
- Summarize, do not re-argue. Reasoning belongs above the summary and is not repeated inside it.

---

## 5. What "the owner" means here

The stack is built for owner-directed, agent-executed development. The agent designs, implements,
verifies, and reports; the owner holds merge authority and product decisions. Every rule that says
"wait for confirmation" or "the owner decides" reflects that split. An agent that advances `main`,
picks a product direction, or edits a sibling project unprompted has overstepped it.
